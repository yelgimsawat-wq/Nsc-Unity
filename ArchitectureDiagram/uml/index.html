แผนภาพ UML ของ Nsc-Unity

แผนภาพ 16 ชุด: ภาพรวมโมดูลทั้งแบบปัจจุบันและแบบที่เสนอ class diagram ของโครงสร้างที่เสนอ sequence diagram ของการสื่อสาร และ data flow กล่อง class แบ่งเป็น 3 ช่อง: ชื่อคลาส (มี stereotype อย่าง <<Interface>> ด้านบนถ้ามี), ฟิลด์ และ เมธอด ไฟล์ที่แก้ต่อใน draw.io ได้อยู่ที่ ArchitectureDiagram/uml/nsc-architecture.drawio มี SVG แยกทีละแผนภาพในโฟลเดอร์เดียวกัน และมีรูป PNG ในโฟลเดอร์ png/

ยกเว้นแผนภาพที่ 1 (โครงสร้างปัจจุบัน) คลาสในแผนภาพเป็นเป้าหมายหลังรีแฟกเตอร์ ยังไม่มีในโค้ดตอนนี้ ดูว่าแต่ละตัวมาจากคลาสเดิมตัวไหนได้ในตารางด้านล่าง

ขนาดแผนภาพ

สัญลักษณ์เส้น

  • Inheritanceสืบทอดคลาส (IS-A)
  • Realizationimplement อินเทอร์เฟซ
  • Associationถือ reference หรือเรียกใช้ประจำ
  • Dependencyใช้ชั่วคราว เช่น เรียก static หรือฟังอีเวนต์
  • Compositionเป็นเจ้าของ ส่วนย่อยอยู่และหายไปพร้อมเจ้าของ
  • Aggregationรวมไว้ แต่แต่ละชิ้นมีอายุของตัวเอง
  • ทิศที่ผิดdependency ที่ไม่ควรมี (แผนภาพ 1)
  • Noteต่อโน้ตอธิบายเข้ากับคลาส
  • Callsequence: เรียกเมธอดหรือ RPC
  • Eventsequence: อีเวนต์หรือค่าที่ sync
  • Replysequence: ค่าที่ส่งกลับ
  • โค้ดปัจจุบันแผนภาพที่วาดจากโค้ดตอนนี้
  • ข้อเสนอยังไม่มีในโค้ด ชื่อคลาสในแผนภาพเป็นชื่อที่เสนอ
  • พฤติกรรมเกมสิ่งที่ผู้เล่นเห็น ต้องเหมือนเดิมก่อนและหลังรีแฟกเตอร์
  • ป้ายในกล่องคลาส{เดิม: X} มาจากคลาส X ในโค้ดตอนนี้ {ใหม่} ยังไม่มีเลย {มีอยู่แล้ว} ใช้ของเดิม
  • โน้ตสีเขียวคงพฤติกรรมเดิม พร้อมค่าตัวเลขจากโค้ดตอนนี้
  • โน้ตสีส้มจุดที่ถ้าทำตามข้อเสนอ ผู้เล่นอาจรู้สึกต่างจากตอนนี้ ต้องลองเล่นเทียบและให้ทีมตัดสินก่อนเปลี่ยน

เครื่องหมายหน้าสมาชิก

  • +public
  • -private
  • #protected
  • {static} สมาชิกแบบ static
  • {abstract} ต้อง override ในคลาสลูก (ชื่อคลาสตัวเอียง = abstract class)
  • {override} override ของคลาสแม่
  • {server only} มีค่าบน server เท่านั้น ไม่ sync

ชนิดของกล่อง

  • ไม่มี stereotype = MonoBehaviour
  • <<Plain C#>> คลาส C# ธรรมดา เทสได้โดยไม่ต้องเปิด Unity
  • กล่องมุมพับ = โน้ตอธิบาย ต่อกับคลาสด้วยเส้นประสีเทา

ภาพรวมโมดูล

1ภาพรวมโมดูล: โครงสร้างปัจจุบันโค้ดปัจจุบัน

แต่ละกล่องคือกลุ่มสคริปต์ตามโฟลเดอร์ในโปรเจกต์ตอนนี้ เส้นสีแดงคือ dependency ทิศที่ไม่ควรมี (เกมเพลย์ชี้ไปหา UI/โหมด หรือวนกลับกัน)

2ภาพรวมโมดูล: โครงสร้างที่เสนอข้อเสนอ

dependency ไหลทางเดียวจากบนลงล่าง UI อ่านได้ทุกอย่างแต่ไม่มีใครพึ่ง UI และ Core ไม่พึ่งใครเลย

Class diagram

3Robot aggregate และวงจรชีวิตของแขนขาข้อเสนอ

หุ่นเป็นเจ้าของลำตัวและแขนขา 4 ชิ้น RobotLimb เป็นตัวแทนของชิ้นนั้นและเป็นที่อยู่ของกติการะดับชิ้น (รับดาเมจเฉพาะตอนต่ออยู่ เลือดหมดแล้วหลุด ต่อกลับแล้วเติมเลือด) สถานะ "ต่ออยู่ไหม" มีเจ้าของคนเดียวคือ LimbAttachment กติกาและตัวเลขทั้งหมดในโน้ตสีเขียวเหมือนโค้ดตอนนี้ ลำตัวดูแผนภาพ 4 ตัวควบคุมดูแผนภาพ 5

4การทรงตัวของลำตัวข้อเสนอ

TorsoBalance ไม่เก็บรายชื่อแขนขาเอง ทุก physics tick มันอ่านแขนขาทั้ง 4 ชิ้นผ่าน Robot มาเป็น BalanceInput แล้วให้ FallRules (คลาส C# ธรรมดา) ตัดสินว่าล้มไหมและเพราะอะไร กติกาและตัวเลขเหมือนโค้ดตอนนี้ทุกข้อ (โน้ตสีเขียว) ส่วนโน้ตสีส้มคือบั๊กที่น่าจะไม่ได้ตั้งใจ แต่แก้แล้วผู้เล่นจะรู้สึกต่าง จึงยังไม่เปลี่ยน

5การควบคุมแขนขาข้อเสนอ

ฝั่งเจ้าของอ่าน input แล้วส่ง RPC แบบ owner-only ฝั่ง server ตรวจค่าแล้วขับฟิสิกส์ ArmController กับ LegController ใช้ฐานเดียวกัน (LimbController) ขามีโหมดเดียวต่อ tick การจับแยกเป็น ArmGrip ส่วนท่าต่อยกับเตะเป็น ability ที่ประกอบเข้ากับ controller ปุ่มและความรู้สึกตอนบังคับเหมือนเดิมทั้งหมด

6เส้นทางดาเมจข้อเสนอ

ผู้โจมตีทุกตัวสร้าง DamageInfo แล้วเรียก DamageRouter ที่เดียว ผู้รับทุกชนิด implement IDamageable กติกาทีมและเฟสของแมตช์จึงอยู่ที่เดียว ฝั่งหุ่น ผู้รับคือ RobotLimb ซึ่งปัดดาเมจทิ้งถ้าชิ้นหลุดอยู่ เหมือนที่ RobotHealth ทำตอนนี้ สูตรดาเมจเดิมย้ายค่าเข้า StrikeTuning

7แมตช์ ลอบบี้ และ sessionข้อเสนอ

MatchSession เป็นเจ้าของเฟสของแมตช์คนเดียว กติกาของแต่ละโหมดเป็นคอมโพเนนต์แยก และ co-op กับ PvP ใช้ระบบแจกแขนขาชุดเดียวกัน เงื่อนไขชนะแพ้และจังหวะการเช็คเหมือนโค้ดตอนนี้

8ไอเทมข้อเสนอ

โครงเดิมใช้ได้ดีอยู่แล้ว ({มีอยู่แล้ว}) สิ่งที่เปลี่ยนคือ HeldItem มี hook ฝั่ง server (HandItemHolder จะได้เลิก cast เป็นปืนชาร์จ) และอาวุธทำดาเมจผ่าน DamageRouter ด้วยตัวเลขเดิม

การสื่อสาร (sequence)

9Sequence: หมัดโดนบอส บอสตาย แมตช์จบข้อเสนอ

ดาเมจเดินผ่าน DamageRouter จุดเดียว บอสแค่ประกาศอีเวนต์ Died โดยไม่รู้ว่าอยู่ในโหมดไหน กติกาของโหมดเป็นคนจบแมตช์

10Sequence: เลือกแขนขา เริ่มแมตช์ ผูกผู้เล่นข้อเสนอ

co-op และ PvP ใช้เส้นทางเดียวกัน LimbSelection เก็บว่าใครคุมชิ้นไหน MatchSession ประกาศเฟส แล้ว binder ในแต่ละเครื่องผูกกล้องกับ input เอง

11Sequence: เลือดหมด ขาหลุด หุ่นล้ม แล้วดึงกลับมาต่อข้อเสนอ

RobotLimb เป็นผู้รับดาเมจของชิ้นและเป็นคนใช้กติกาของชิ้น LimbHealth กับ LimbAttachment ไม่รู้จักกัน Robot สั่งลำตัวล้มพร้อมเหตุผล ลำตัวไม่ต้องถอนทะเบียนขา เพราะ tick ถัดไปมันอ่านแขนขาจาก Robot เอง ส่วนการแพ้เป็นหน้าที่ของกติกาโหมด ลำดับและตัวเลขเหมือนเกมตอนนี้

12Sequence: ก้าวเท้าหนึ่งครั้ง จาก input ถึงจอทุกคนข้อเสนอ

ใครเป็น authority: เจ้าของขาส่งแค่คำสั่ง server ตรวจคำสั่ง จำลองฟิสิกส์ และตัดสินการล้มคนเดียว ทุกเครื่องได้ผลผ่าน NetworkTransform (AuthorityMode = Server) และ NetworkVariable ไม่มีการทำนายผลฝั่ง client

13Sequence: ตกแมพแล้วเกิดใหม่ที่เช็คพอยต์ข้อเสนอ

RespawnManager ตัดสินว่าเมื่อไหร่และที่ไหน Robot ตัดสินว่ารีเซ็ตตัวเองอย่างไรและตามลำดับไหน ชิ้นส่วนแต่ละชิ้นล้าง state ส่วนตัวของตัวเอง Robot ไม่รู้จักชิ้นส่วนข้างในแขนขา (เช่น ArmGrip) แค่สั่ง LimbController ทีละชิ้น และอ่าน joint ปัจจุบันจากแขนขา ไม่ใช้ลิสต์ที่แคชไว้ตอนเริ่มฉาก การต่อแขนขาที่หลุดและเลือดคงไว้ตามโค้ดตอนนี้

Data flow

14Data flow: ค่าตั้ง → state → ลอจิก → การแสดงผลข้อเสนอ

ค่าตั้งอยู่ใน asset ลอจิกรันบน server state ที่ sync มีเจ้าของคนเดียว และการแสดงผลแค่อ่าน state ไม่แก้เอง

พฤติกรรมเกมที่ต้องคงไว้

15พฤติกรรมที่ผู้เล่นเห็น: ลำตัว แขนขา และแมตช์พฤติกรรมเกม

State machine ของสิ่งที่ผู้เล่นรู้สึกได้ วาดจากสคริปต์และค่าใน prefab ที่ฉากเกมใช้จริง (Yelmee/RobotContainer) ใช้เป็นสัญญาว่าหลังรีแฟกเตอร์ทุกสถานะ ทุกเส้น และทุกตัวเลขต้องเหมือนเดิม แผนภาพที่เสนอทุกแผ่นต้องทำให้ได้ผลแบบนี้

Class diagram รวมภาพเดียว

16Class diagram ทั้งระบบในภาพเดียวข้อเสนอ

ทุกคลาสของข้อเสนอรวมในแผ่นเดียว ใช้เส้นแบบเดียว: ลูกศรชี้ไปยังคลาสที่ถูกใช้หรือถูกถือ reference หัวลูกศรสองข้างคืออ้างถึงกัน การสืบทอดและ implement เขียนในชื่อแบบ A : B enum กับ struct ไม่ลากเส้น
